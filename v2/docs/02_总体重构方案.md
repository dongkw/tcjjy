本方案保留 dsh 插件的总体方向。2026-10-26 起，实施顺序以 [04 分阶段实现方案](04_分阶段实现方案.md) 为准：先本机运行、先数据与规则，使用 PostgreSQL + pgvector 单库，向量检索、RAG 和长期记忆是正式学习内容，兼容适配后置。[03 功能清单](03_dsh插件功能清单.md)作为完整功能目录；Agent 八个开发方面的职责对应见 [01 对应说明](01_Agent开发八件事与项目对应.md)，检索与记忆设计见 [05 方案](05_向量检索与长期记忆.md)。此前自建 Python Agent 运行框架的方案已被本方案替代。本文后续阶段是能力划分，不是首个可运行版本的门槛；交易内核按 04 的数据库方式逐段实现，不单独建设一致性、镜像或对账系统。

## 1. 交付目标

开发一个可以挂载到 dsh 的股票研究插件。在对话中接收研究目标，供模型调用行情、公告、财务、账户和策略工具，产出有证据的研究结果与受限模拟计划。

研究阶段的目标是研究与风控预演，后续连接自动模拟交易并验证收益。目前已实现数据库、行情、规则、资料切块、本地向量化及检索接口；Agent、长期记忆与交易尚未实现。

## 2. 职责划分

| 组件 | 负责什么 | 采用方式 |
| --- | --- | --- |
| dsh 宿主 | 模型调用、工具循环、会话日志、通用上下文管理、工具事件与交互 | 复用现有机制，通过受支持扩展点配置 |
| TypeScript 插件 | 工具 Schema、注册与注销、股票研究 preset/任务指令、参数及结果适配、业务访问约束 | 独立插件项目，挂载到 dsh，不修改宿主核心 |
| Python 业务能力 | 数据适配、指标、策略、证据、计划、后续回测和模拟交易 | 从旧项目提取并验证，必要时通过本地服务供插件调用 |
| 业务存储 | 证据、快照、报告、计划修订、后续订单和资金持仓事实 | 与 dsh 会话存储分开管理，业务记录关联 session/call ID |
| 后续执行 worker | 有效计划的持续监控、风控重检、撮合、幂等、对账 | 独立持续运行，不依赖聊天页面打开 |

TypeScript 是原生插件层的选择；Python 是保留数据和量化能力的选择。先定义稳定业务契约再确定调用协议，首轮只实现一条插件到业务的接入路径。MCP 可供以后跨应用复用，不同时开发多套桥接。

依据本地 dsh 的 [工具编写参考](D:/deepseek/deepseek-harness/docs/cookbook/adding-a-tool.zh.md)、[工具入门](D:/deepseek/deepseek-harness/docs/user/develop/basic/tool.zh.md)、[preset 说明](D:/deepseek/deepseek-harness/packages/preset/agent-presets/README.zh.md)；这些是宿主现有能力的参考，具体业务工具尚未存在。dsh 为开发预览，开发时固定兼容版本并验证插件加载与行为。

## 3. 用户体验与执行关系

示例任务：

> 检查自选股和模拟持仓近期风险，缺资料就补查，生成下一交易日的模拟计划，说明依据与失效条件。

运行关系：用户在 dsh 提出任务 → 模型选择插件工具 → 插件校验并调用业务能力 → 返回结构化结果及证据 → 模型继续补查或提交研究 → 业务校验器保存报告、计划和预演结果。

模型选择查询顺序、分析材料并识别缺口。程序计算指标、策略、仓位和成本，验证证据、时间、权限及计划结构。不得用模型自报的“完成”跳过业务结果检查。

后续自动执行关系：有效计划 → 新的可执行报价 → policy/账户版本与风控重检 → 模拟订单与撮合 → 事务账本 → 对账与绩效。此流程不要求每个报价事件都调用模型。

## 4. 旧能力的取舍

| 旧项目能力 | V2 处理 |
| --- | --- |
| 行情、财报、公告接口 | 提取适配器，补来源、时效、单位、失败分类与缓存 |
| 分析快照、特征、策略证据契约 | 保留有价值的设计，统一为业务工具输出 |
| 趋势、退出、硬否决等纯规则 | 作为待验证策略素材，分清研究策略和可执行基线 |
| AI 输出证据引用和字段校验 | 提取为结果检查，不继续通过旧 CLI 摘要调用嵌套 Agent |
| 成本、可卖量、交易约束 | 保留业务要求与可验证公式，新交易内核重新验收 |
| 策略 fixture 与测试 | 迁入相应业务回归，另增加 dsh 集成与 Agent Evals |
| 旧工作流、多入口、独立聊天页面 | 由 dsh 对话与插件工具替代，按需保留业务展示 |
| JSON 主账本和 SQLite 镜像链路 | 不继续作为自动交易事实源；后续使用单事务业务账本 |

旧代码和账户影子材料先作为只读参考，新模拟账户独立初始化，不把旧影子账户转为可执行账户。原始审查与缺陷证据保存在 [前期审查方案](../../docs/Agent核心重构与自动模拟交易方案_v0.3.md)，其中旧技术方向仅作为历史参考。

已发现的重复成交、陈旧报价成交、多文件记账、回放时钟冲突和回撤计算问题，必须转换为新内核的行为验收。旧策略测试通过不代表上述问题已解决。

## 5. 数据和状态边界

- dsh 会话记录用于工具历史、上下文和交互恢复；证据、计划及账户事实由业务存储承担。
- 每份资料记录公司、期间、来源、发布时间/可用时间、抓取时间及原文位置；查询日不能替代行情事件时间。
- 研究快照与成交报价分开。计划保存数据、策略、policy 和账户版本及有效时段。
- 通用工具参数类型由 dsh 机制校验；账户绑定、证券范围、跨字段条件、证据支持关系和时效由插件/业务层检查。
- 插件注销、取消和后端故障需有明确行为。研究可返回数据缺口，不把来源超时当成“没有风险”。
- 业务恢复通过稳定 artifact/plan/job ID 查询，不因 dsh 恢复对话而假定外部任务也恢复。
- 后续订单、成交、现金、持仓与锁仓需事务和业务幂等；会话 call_id 仅作关联，不能作为唯一的业务去重依据。
- 首版不开放真实交易和任意 SQL/shell 工具；模型不能变更资金事实或提高 policy 上限。

## 6. 分阶段实施

| 阶段 | 重点交付 | 验收重点 |
| --- | --- | --- |
| V0.1：dsh 研究插件 | 加载/配置、只读上下文、数据和证据、策略、计划、风控预演、报告、评测 | 真实模型能按结果补查，引用有效，预演不改变账户 |
| V0.2：自动模拟交易 | 订单与撮合、事务账本、持续执行、暂停/取消、重启恢复与对账 | 重试和并发无重复成交，崩溃无半笔交易，过期数据不成交 |
| V0.3：收益实验 | 统一策略回测、成本/净值/基准、样本外与前向对照 | 时间可见性正确、指标可核对、实验全部留档 |

后续支持范围从明确的普通沪深主板 A 股开始，特殊证券和交易制度在实现前排除或单独适配。市场规则按证券类别与生效日期维护。

首版可从导入的只读模拟持仓快照和固定数据样例起步，明确标记数据模式。研究结果允许“证据不足”“继续观察”和“无有效计划”，不以强制给出买入结论作为成功标准。

## 7. 验证原则

1. Agent Evals 检查是否用对工具、必要资料是否补齐、结论是否有据、能否在限制内结束；真实模型集成验收与离线假模型测试分别记录。
2. 工程测试检查插件加载/卸载、权限、取消、后端失败、版本兼容和业务持久化；交易阶段另做幂等、事务和市场约束测试。
3. 交易实验冻结策略与 policy，用同一业务实现贯穿回测和模拟盘，纳入费用、滑点、缺数、停牌与公司行动。
4. 实验按时间划分开发、验证和最终样本外区间，记录所有参数尝试；前向比较规则基线与规则加 Agent，保持资金、股票池和执行约束一致。
5. 报告交易净收益、最大回撤、基准、样本量与分阶段表现，同时记录数据/模型成本。模拟结果不直接外推真实成交。
6. 历史 LLM 研究可能受模型后来知识影响；仅限制查询工具日期不能完全消除，AI 增量主要依靠冻结版本后的前向观察。

研究质量、系统可靠性与收益表现分别验收。盈利是需要通过数据证明的实验结果，不能以增加角色、工具数量或漂亮的单次回测替代验证。
