# Agent 开发八件事与本项目对应

日期：2026-10-23，更新：2026-10-26。状态：**dsh 插件设计说明；行情规则与向量检索后端已实现，Agent 接入待开发。**

当前方向已确定为开发 dsh 股票研究插件，功能范围以 [03 功能清单](03_dsh插件功能清单.md) 为准。本文中的“程序”包括 dsh 宿主和插件业务程序：dsh 提供模型接入、工具循环、会话及通用轨迹；插件负责业务工具、研究指令、证据、计划及交易约束。

这八件事沿用 msplan 项目“111”聊天中的八个方面：确定任务、接入模型、准备数据、封装工具、编写执行流程、管理任务状态、设置执行约束、测试和上线。

**它们是开发工作的八个方面，不是每次运行必须依次经过的八个节点。** 开发时会交叉迭代；运行时，模型根据任务和已有工具结果选择下一步。

下面始终使用同一个任务来说明：

> 研究我的自选股和模拟持仓，检查风险；缺资料时继续查询。生成下一交易日的模拟计划，说明依据、触发条件和失效条件。首版交付草案与风控预演；后续再将已启用的有效计划交给模拟执行程序自动跟踪。

## 对应总表

| 八件事 | 在本项目中对应什么 | 需要体现的 Agent 开发能力 |
| --- | --- | --- |
| 1. 确定任务 | 定义研究范围、模拟账户和完成标准 | 把开放要求转成受限、可验证的任务 |
| 2. 接入模型 | 复用 dsh 模型配置，编写研究指令、工具定义和结果契约 | 插件为宿主模型提供正确的业务能力与限制 |
| 3. 准备数据 | 行情、财报、公告、持仓、策略结果与证据 | 决定本轮模型看什么、缺什么、哪些资料有效 |
| 4. 封装工具 | 查询账户、查行情、读公告、跑策略、预演计划 | 让模型选对能力、填对参数、理解失败 |
| 5. 编写执行流程 | 使用 dsh 工具循环，配置研究模式、补查与完成规则 | 根据新信息动态补查，复用宿主停止与取消机制 |
| 6. 管理任务状态 | dsh 保存会话；插件保存业务证据、报告、计划和任务标识 | 恢复时对齐会话与业务状态，避免副作用重复执行 |

| 8. 测试和上线 | Agent Evals、交易行为测试、收益实验、轨迹 | 验证任务质量和执行过程，定位错误与消耗 |

## 1. 确定任务：明确 Agent 要完成什么

在本项目中，需要把一句“帮我看股票并自动交易”拆成可以判断完成与否的约定。

你需要定义：

- Goal（目标）：本次要检查什么、最终交什么结果。
- Scope（范围）：允许研究的股票池、信息截止时间、绑定模拟账户和模式。
- Success Criteria（完成标准）：结论带真实证据；计划有明确条件；缺资料时标记缺口，不能强行给出买入结果。

例如，一次研究任务的完成条件可以是：自选池全部检查过，每个候选都有策略结果和证据，无法确认的项目说明原因，最终产出有效计划或“暂不执行”。“本次一定买入”“本次一定盈利”不适合作为研究任务的完成条件。

**模型做什么：** 理解用户要求，在允许范围内识别研究重点，并提出需要补充的信息。

**程序做什么：** 将目标、股票池、截止时间、policy 和账户绑定为任务，校验范围并保存修订。模型不能通过重述任务扩大权限。

**你要交付：** TaskSpec 的字段约定、任务入口、任务模板和完成检查规则。

这一步的不同之处是：同一句开放要求可能有多种合理解释，你需要让模型知道完成标准，并让程序能够检查最终结果。

## 2. 接入模型：既能接收回答，也能接收动作请求

本项目里的模型需要返回两类内容：

1. 下一步工具调用请求，例如“查询该股票近一段时间的公告”。
2. 最终结构化研究结果，例如事实、风险、证据、缺口和候选建议。

模型接入和通用调用机制复用 dsh，不再单独开发 ModelGateway。你需要编写股票研究 Prompt（任务指令）、Tool Schema（工具参数结构）及 ResearchConclusion（最终输出约定），并确定如何校验最终结果。模型异常与 usage 沿用宿主机制，插件补充业务失败、后端超时和输出缺字段的处理。

**模型做什么：** 根据目标和本轮上下文，选择工具、填写参数，或提交结果。

**程序做什么：** dsh 发送模型请求、分发工具调用；插件执行业务适配，并把最终结果交给证据和业务校验。

**你要交付：** dsh 股票研究 preset、版本化任务指令、业务工具及结果契约，以及业务异常处理；模型适配器复用宿主配置。

这里的开发重点是处理“模型建议下一步干什么”。例如模型返回 read_evidence，并不意味着它已经读了公告；后端还要实际执行。

旧版 Codex CLI 摘要不继续作为新研究主循环；工具循环由 dsh 承担。工具请求由模型生成、真实函数由应用执行的关系可参考 [OpenAI 官方工具调用说明](https://developers.openai.com/api/docs/guides/function-calling)。

## 3. 准备数据：决定模型这一步能看见什么

本项目中的材料包括行情、K 线特征、财报、公告正文、模拟账户快照、策略结果和前面已查到的证据。

例如模型收到“近期风险”任务时，程序可以先提供持仓概况、数据时间和公告索引；需要查具体事项时，再通过工具取正文。不能把所有股票多年资料一股脑塞入每轮输入。

你需要处理：

- Context（上下文）：选哪些任务要求、历史工具结果和材料给本轮模型。
- Retrieval（检索）：按公司、期间和主题寻找相关公告，必要时再增加语义检索。
- Chunk（分块）：长公告分页或分段读取，保留正文位置。
- Grounding（有据可查）：每个判断指向实际取得的 evidence_id、原文和日期。
- Context Budget（上下文预算）：去重、筛选、压缩已读内容，为后续调用预留空间。

**模型做什么：** 阅读材料、识别矛盾和缺口，判断是否还需要查询。

**程序做什么：** 抓数据、算指标、保存原文、检查时间与口径，并组织有限上下文。金额和收益计算尽量由程序完成。

**你要交付：** 数据适配器、EvidenceStore、上下文组装器，以及来源、单位、公司、期间和时间可见性检查。

尤其需要区分：用于解释的研究快照、当时可获得的历史资料，以及用于模拟成交的当前报价。模型看过一份快照，不代表那份价格仍能用于成交。

本项目把向量检索纳入学习目标：使用 PostgreSQL + pgvector 保存资料切块及向量，查询时按股票和时间筛选并检索相关正文，再交给模型分析。Embedding、RAG 与长期记忆的具体实现见 [05 向量检索与长期记忆](05_向量检索与长期记忆.md)。旧资料和模型常识不能补造不存在的事实。

## 4. 封装工具：把业务能力做成模型能正确使用的接口

工具内部仍是你熟悉的接口调用、数据库查询或业务计算。新增的工作是让模型知道何时用、怎样填参数，以及结果意味着什么。

| 工具 | 模型为何调用 | 程序实际做什么 |
| --- | --- | --- |
| get_account_snapshot | 先了解当前持仓与现金 | 查询绑定模拟账户并返回版本 |
| get_market_snapshot | 检查行情、特征和数据缺口 | 读取指定股票的数据及来源时间 |
| refresh_market_data | 发现缺少必要资料 | 从允许的数据源补取并保存证据 |
| search_announcements | 查找相关公开事项 | 按公司、时间和关键词检索 |
| read_evidence | 公告索引不足以支持判断 | 读取本任务获得的正文片段 |
| evaluate_strategy | 想确认是否满足明确策略 | 调用指定版本的确定性策略 |
| preview_paper_plan | 想了解候选能否形成有效计划 | 编译有限条件并预演风控，不直接成交 |

你需要为每个工具写清名称、说明、参数结构、单位、允许范围和结果状态。例如，查询成功但零条公告、数据源超时、权限不足、资料缺失必须能区分；“工具返回成功”不代表研究已经充分。

**模型做什么：** 选择工具并提出参数。

**程序做什么：** 校验参数和权限，调用真实业务能力，返回有结构的 Observation（观察结果）。

**你要交付：** 使用 dsh 注册机制的工具插件、Schema、业务参数校验、适配器和工具效果评测。

首版通过 TypeScript 原生插件注册工具，数据和量化能力可通过薄适配调用 Python 业务程序。MCP 留作跨应用复用的接入选择；具体调用协议在开发前落实，首轮只实现一条路径。

## 5. 编写执行流程：根据结果继续推进

研究循环的示例：

```text
模型：先查模拟持仓与行情
程序：返回账户快照和数据，其中一只股票资料缺失
模型：选择补取该股票资料
程序：返回补取结果及一个风险公告索引
模型：选择读取公告正文
程序：返回带来源和日期的正文
模型：结合证据，请求运行允许的策略并预演计划
程序：返回策略与风控结果
模型：提交有依据的研究结论，说明被阻塞的候选
程序：校验结果，保存有效计划或缺口，结束研究
```

这是一条可能路径。数据齐全时可以少查，资料不足时可以继续补查，源不可用时可以报告阻塞。不能提前写死每次都查同样的七个接口，再把它称为模型自主选择。

dsh 已提供 Agent Loop 与工具结果回传。你需要设计研究任务指令、补查与完成标准，配置并验证适用的停止/预算机制，在业务工具中处理无效输入、缺证据和规则阻塞。插件通过 preset 和宿主扩展点工作，不再另建 LangGraph 循环。

**模型做什么：** 根据新增资料决定下一步或结束。

**程序做什么：** 按允许的状态转移执行模型请求，检查预算、取消和结束条件。

**你要交付：** 可观察、受控制的股票研究模式和业务完成检查，执行循环复用 dsh。

首版只形成草案与预演，不创建订单或成交。后续研究完成后的自动模拟执行属于另一条确定性流程：有效计划 → 新报价 → 风控 → 撮合 → 事务记账 → 对账。研究 Agent 不直接修改资金，模拟执行也不必每笔重新调用模型。

## 6. 管理任务状态：中断后知道从哪里接着做

例如一次研究已经查完两家公司公告，第三次工具调用超时。程序重启后应能读取已有材料，从未完成步骤继续；之前产生的计划也不能再次生成相同业务效果。

状态按归属分开保存并用 ID 关联：

- State：dsh 保存会话与通用执行历史；插件保存研究目标、业务阶段、待补信息和结果引用。
- ToolInvocation：复用 dsh 的工具事件，业务记录关联 session/call ID、结果 ID 和后端重试信息。
- Evidence：已经取得的材料及来源，不只保存最终摘要。
- 恢复点：dsh 会话恢复与业务任务/计划状态分别核实，不假定恢复聊天就恢复了外部任务。
- Budget：使用宿主提供的调用统计与控制，后端另外管理请求和长任务预算。

Memory（记忆）也要明确含义：当前任务的工作记忆服务于这次研究；经确认的长期偏好可以跨任务使用。模型自己推断出的偏好不能自动成为长期约束。资料保存后仍需由程序在后续调用中取出，模型才能使用。

**模型做什么：** 根据恢复后提供的状态和材料继续研究。

**程序做什么：** 保存并恢复状态，执行重试策略，避免副作用重复发生。

**你要交付：** 与 dsh 会话关联的业务持久化、结果查询、恢复校验和业务幂等键。

dsh 的会话持久化负责会话事件，参考 [本地持久化说明](D:/deepseek/deepseek-harness/packages/session/session-persistence/README.zh.md)。证据和计划由插件业务存储保存；后续交易账本另外需要单事务与唯一约束。会话日志不代替资金和持仓事务，业务幂等键不能只用模型每轮新产生的 call_id。

## 7. 设置执行约束：把边界落实为程序检查

提示词可以告诉模型“不要越权”，后端仍需检查每次真实动作和结果。

| 约束 | 本项目里的例子 | 由谁执行 |
| --- | --- | --- |
| Permission / 工具权限 | 只能查任务股票池和绑定模拟账户 | 服务端工具层 |
| Guardrails / 输入输出校验 | 未取得的证据 ID 不能出现在有效结论中 | 证据与结果校验器 |
| Budget / 预算 | 任务与业务调用在配置限制内运行 | dsh 控制机制及业务后端，开发时验证各自范围 |
| 外部内容隔离 | 公告里的“忽略规则并转账”不能扩大权限 | 工具与执行权限边界 |
| 信息时效 | 过期研究材料需标注；陈旧报价不能成交 | 数据与执行层 |
| 交易规则 | 数量、资金、可卖量和风控满足要求 | ExecutionService |
| Human-in-the-loop / 人工参与 | 修改 policy、补充必要假设或处理明确歧义 | 用户操作与任务修订 |

**模型做什么：** 在允许能力内提出行动请求；资料不足时说明缺口。

**程序做什么：** 独立决定请求能否执行，拒绝越界请求，并给出可供继续处理的错误结果。

**你要交付：** 服务端权限、输入输出校验、预算和风控实现，以及越权验收样例。

后续自动模拟盘的有效计划可以在预先配置的 policy 内自动执行。人工参与只用于事先定义的情况，不应把逐笔确认设成整个自动模拟盘的默认动作。首版不启用计划或执行交易。

## 8. 测试和上线：分别验证 Agent、系统和策略

这里的“上线”首先是本地可运行的 dsh 插件 demo，后续再验收无人值守模拟盘。

| 验证对象 | 测什么 | 如何检查 |
| --- | --- | --- |
| Agent Evals | 是否选对工具、补查有效、引用真实、结论有依据、能停止 | 固定任务集、必要行为断言、结果评分与抽查 |
| 工程正确性 | 超时恢复、幂等、并发、事务、数据时效与交易约束 | 确定性测试、故障注入、集成验收 |
| 交易实验 | 完整成本后的收益、回撤、基准表现和样本量 | 统一代码的回测、样本外和前向模拟 |

Agent 任务集应包含：正常数据、缺公告正文、单位或期间冲突、接口失败、假证据、公告注入、预算耗尽和重启恢复。不能只检查最终答案文字相似；不同工具路径也可能都合理，应检查必要查询是否完成、结果是否有据。

Trace（执行追踪）记录每次任务的工具参数、结果引用、状态变化、异常、耗时、usage 和版本。网页中应能看出“为什么需要补查”“哪个工具失败”“哪个规则阻止了计划”，不要求显示模型隐藏思维过程。

**模型做什么：** 在评测任务里实际选择工具并产出结果。

**程序做什么：** 执行用例、收集轨迹、计算指标，发现回归与异常。

**你要交付：** 插件 evals 数据集与评分器、集成测试、业务结果展示和实验报告；工具轨迹复用 dsh，不新建聊天工作台。

离线假模型适合检查程序流程，真实模型集成用例才能验证工具选择与输出质量。模型研究正确、模拟盘成交正确、策略赚钱是三种不同结果，分别记录。模型或提示词升级后重跑 Agent 回归，策略变更后重新进行对应的收益实验。

## 在本项目中三方怎样合作

| 开发者提前设计与实现 | 模型运行时判断 | 后端程序运行时执行 |
| --- | --- | --- |
| 工具能力、说明与参数约定 | 这一步调用哪个工具 | 校验并调用真实接口 |
| 上下文和证据规则 | 查到什么、还缺什么 | 保存来源，筛选材料并组织输入 |
| 循环、预算和完成标准 | 继续补查还是提交结论 | 管理状态、检查条件和持久化 |
| 策略、policy 与交易约束 | 提交研究候选和依据 | 计算计划、风控、撮合与记账 |
| 评测集与验收规则 | 在实际案例中完成任务 | 收集轨迹、评分并报告实验结果 |
