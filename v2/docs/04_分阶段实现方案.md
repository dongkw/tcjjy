# V2 分阶段实现方案：先在本机跑起来

日期：2026-10-26。状态：第 1～2 段已实现并验证；第 3～7 段待开发。

当前按本方案安排开发顺序。[03 功能清单](03_dsh插件功能清单.md)保留为功能目录，不要求一次做完。本项目也是 Agent 开发学习项目，向量检索、RAG 与长期记忆正式纳入开发。dsh 插件方向保留，先使用本机 dsh Web；桌面适配、多模型切换、插件发布和专用界面以后再做。

## 1. 先确定的实现方式

- Python + FastAPI 实现行情、规则、研究记录、计划与模拟盘。
- TypeScript 薄插件把这些能力接到 dsh，模型调用和工具循环继续用 dsh。
- 使用 PostgreSQL + pgvector 一个数据库：普通表存行情、报告、计划和账户，向量列存公告、报告与记忆的检索向量。不再用业务 JSON 文件或数据库镜像。
- Embedding 先采用本地中文模型 `BAAI/bge-small-zh-v1.5`，学习切块、向量化、语义检索和检索增强生成；详细范围见 [05 方案](05_向量检索与长期记忆.md)。
- 先用 3～5 只自选股、一个数据源、一条明确规则、日频研究；范围先限于支持的普通沪深主板股票。
- 模型先用本机 dsh 中已经可以调用的一个提供商，不把 GPT 新模型配置或订阅适配作为业务开发前置条件。

运行关系：dsh 对话 → 股票工具插件 → 本地 Python 接口 → PostgreSQL + pgvector；Python 同时调用本地 Embedding 模型完成向量化。

## 2. 七段交付

| 段 | 本段实现 | 完成后能看到什么 | 验收 |
| --- | --- | --- | --- |
| 1. 数据和规则先跑通 | 新建 V2 Python 环境、本地接口、PostgreSQL + pgvector；接一个数据源，提取一条纯规则，准备入库样例 | 输入股票代码，得到行情、指标、规则结果和缺失字段 | 本地服务能启动；样例与真实抓取模式明确区分；数据和结果写入数据库 |
| 2. 向量检索先独立跑通 | 公告入库、切块、本地 Embedding、相似度检索、股票/时间过滤 | 用不同措辞提问，也能找到有关原文及出处 | 固定问题能命中预期片段；不同公司和未来资料被过滤；无相关资料能返回空 |
| 3. 接上 dsh 做研究与记忆 | 查股票、语义检索/读原文、跑规则、保存/查询报告、保存/召回记忆；提供研究指令 | 模型自主补查、引用检索结果，并在新会话里想起相关历史 | 真实模型完成研究和补查；新会话召回已存记忆；报告引用可回查 |
| 4. 生成计划和风控预演 | 计划草案、触发/失效条件、有效期；代码计算数量、仓位与费用 | 报告进一步给出“可以考虑怎样执行”及拒绝原因 | 有效草案、无候选和资料不足都能解释；此时不下单、不改变持仓 |
| 5. 跑通虚拟盘 | 初始化独立模拟账户，实现基础订单、日频撮合、费用、现金、持仓和净值 | 手动触发一次流程，看到计划、模拟成交、持仓和收益变化 | 数据库中的资金变化和成交可核算；少量历史日期重放通过后进入下一段 |
| 6. 让虚拟盘自动运行 | 本地定时任务串起取数、研究、计划、执行、日终记录；提供启动、暂停、停止 | 不需要每天手工发指令，能连续运行多个交易日 | 关闭聊天页面后任务仍能运行；失败有记录，缺有效数据时不成交 |
| 7. 验证策略和 Agent 的作用 | 用同一套规则与交易代码做回测、前向模拟；比较纯规则与加入 Agent 的结果 | 收益曲线、回撤、费用，以及 Agent 有没有改善决策 | 版本与区间可回查，完整展示盈利或亏损，不能用单次演示代替收益证据 |

第一段结束就有可运行的业务结果，第二段能演示向量检索，第三段能演示使用 RAG 和长期记忆的 Agent。逐段交付，再补计划和交易。

### 第 1 段：只提取马上用得上的旧能力

从旧项目提取行情请求、指标计算和纯规则，不把整套旧入口搬进 V2。新建独立 Python 环境，不依赖旧 `venv` 的机器路径。

首个接口只需支持健康检查、股票数据查询和规则计算。原始资料、字段来源与时间一起入库；缺字段明确返回，不用模型猜数。

样例数据也放数据库，通过单独命令导入。它用于没有网络时检查业务流程，真实行情抓取另做验收。

### 第 2 段：单独学清楚向量检索

先把一批带来源的公告和报告存库，切成保留原文位置的小段，通过同一个 Embedding 模型编码后存入向量列。问题也向量化，结合股票、类型和时间条件检索，返回正文而非只返回分数。

先用精确向量距离检索验证效果，再以 HNSW 索引作为扩展练习，比较耗时与召回。检索流程先不依赖对话模型，以便单独检查切块和召回问题。

### 第 3 段：先交付一种研究任务

示例：研究指定股票近期情况，运行规则，检查相关公告，说明目前依据和信息缺口。

插件先用 dsh 通用工具展示，不做股票大屏。公告支持条件查询、语义检索和原文读取；完整财报解析以后再扩展。

工具返回真实数据与来源，模型负责决定查什么、是否补查及怎样组织报告。报告正文和引用关系存库，后续可追问。

### 第 4 段：把研究变成可检查的草案

计划只接受少量明确条件，字段包括股票、方向、依据、触发/失效条件和有效期。数量与费用由代码计算。没有合适候选时，返回“暂无计划”也是正常结果。

### 第 5 段：先支持最简单的模拟交易

建立独立模拟账户，使用固定初始资金；账户数据保存到 PostgreSQL 普通业务表。首版做基础买卖与完整成交，不扩展复杂委托、部分成交或分钟级交易。

首先使用明确的日频模型：交易日收盘后研究，下一交易日按已定义的开盘撮合规则处理。停牌、缺行情或无法确认可成交时，保持未成交或拒绝；前向运行只能使用当时已经取得的有效报价。

这一段就做短区间历史重放，检查交易时间、费用、初始净值和持仓计算。正式收益比较放第 7 段，基础计算不能等到最后才验证。

### 第 6 段：普通本地定时任务即可

一个 Python 后台进程执行日频任务，任务状态、结果和失败原因存库。dsh 用于发起研究、查询结果和控制任务，持续运行由业务进程负责。

先提供启动、暂停和停止，不建设通用调度平台，也不新增外部通知渠道。

### 第 7 段：再投入策略改进

先固定策略、股票池和费用参数，形成纯规则基线，再观察加入 Agent 后的收益、回撤和成本。数据时间与策略版本从第一段起记录，历史回放不能看到当时尚未公开的资料。

历史模型分析仍可能受模型后来知识影响，因此 Agent 的增量价值还要通过后续真实时间推进的模拟观察。结果允许盈利、亏损或样本不足。

## 3. 数据库先按需要逐段建表

| 建表时点 | 表的用途 |
| --- | --- |
| 第 1 段 | 自选股、行情/指标、资料正文与来源、规则结果 |
| 第 2 段 | 资料切块、向量、来源版本与检索评测样例 |
| 第 3 段 | 研究报告、报告引用、长期记忆及其向量 |
| 第 4 段 | 计划、预演结果 |
| 第 5 段 | 模拟账户、订单、成交、持仓、每日净值 |
| 第 6 段 | 定时任务与运行记录 |

不提前搭建通用数据平台。金额、数量、日期、状态等需要查询和计算的字段使用普通数据库列；正文使用文本列。接口返回结构化数据不等于另存业务 JSON 文件。

## 4. 长期记忆与向量检索

使用同一个 PostgreSQL 数据库中的 `agent_memory` 表，字段包括编号、用户/账户范围、类型、股票代码、内容、来源、更新时间、失效时间、向量与 Embedding 模型版本。

只保存用户明确偏好、尚未完成的研究事项、有出处的复盘经验。普通聊天和完整工具结果不反复复制为记忆。

开始研究时先限定用户/账户、股票、类型和有效期，再按语义检索少量相关记忆，加入本次上下文。完整历史结论按需查询研究报告。账户资金和持仓仍精确读取业务表，不能用模型写的记忆替代。

资料检索与长期记忆复用同一个向量化模块，但各自保存来源、有效期与类型。详细读写规则、模型选择和验收见 [05 向量检索与长期记忆](05_向量检索与长期记忆.md)。
